# SDTM Define-XML workflow (full detail)

Repeatable workflow (v0.1) for building and QC-ing an SDTM Define-XML spec — the
Excel format Pinnacle 21 (P21) reads, tabs `Datasets`, `Variables`, `ValueLevel`,
`Codelists`, `Dictionaries`, `Methods`, `Comments`, `Documents`, `Standards`. This
mirrors the team SOP `SDTM_Define_Workflow_v0.1.docx`.

## The one rule that matters most

**Never make anything up.** Every value — Origin/Source, CRF pages,
Method/Comment/algorithm text, dataset labels, class, codelist terms, standard/CT
versions — comes **only** from **guidance** (CDISC SDTM-IG / Controlled
Terminology / Define-XML) or the **specs** (the TD SDTM spec, the P21-generated
define, the VLM, the aCRF, or the actual SDTM data). If no source has it, **leave
the cell blank and flag it** (highlight + Programmer Review column) — a flagged
empty cell is safer than a wrong-but-plausible one. Copy sourced text **verbatim**;
do not paraphrase into something that reads better.

## Inputs (three)

1. **Define spec generated by P21 Enterprise/Community** from the study's
   validation data (the SDTM `.xpt` datasets). This is the **starting workbook** —
   it already carries the study ID, SDTMIG version, Define-XML version, CT
   version, and the Datasets/Variables/Codelists **skeleton** from the data.
2. **TD SDTM specs** (compound spec, one column per study) **+ VLM** *(optional)* —
   the **fill sources** for Origin/Source, Pages, Methods, Comments, value-level.
3. **Annotated CRF (aCRF)** — authoritative source of CRF page numbers.

Model: **P21 builds the skeleton → enrich it from the TD specs (+ VLM) → use the
aCRF for pages.** The standards/identity metadata is pre-filled by P21 — **verify**
it (do not invent it).

**Run [scripts/fill_define.py](../../scripts/fill_define.py) for the fill** rather than
hand-writing one per study — it implements every rule below and is study-agnostic
(the study ID, versions, domains, pages and text all come from the inputs):

```
python scripts/fill_define.py --skeleton <p21_define.xlsx> --spec <td_spec_sdtm.xlsx>     --acrf <acrf.pdf> --out <define_filled.xlsx> [--vlm <td_spec_vlm.xlsx>]     [--study <STUDYID>] [--sibling <sibling_define.xlsx>] [--page-ref physical|printed]     [--ct <YYYY-MM-DD>] [--subject-domains QS] [--domain-vl inherit|flag|acrf] [--vendor-domains LB,LC]
```

Ask the user (do not assume) before choosing: the CT version when it may differ
from the spec's Study tab (`--ct`); whether QS answers are Subject or Investigator
(`--subject-domains ""` for Investigator); and how to treat skeleton **domain**
value-level rows that have no VLM column for this study (`--domain-vl inherit`
copies the parent variable's spec row; `flag` leaves them blank + orange); `acrf`
fills per test: a Collected/Investigator parent gives Collected + that test's own
aCRF pages where the where-clause value is annotated, unannotated `--ORRES` tests in
`--vendor-domains` (spec source is a vendor transfer, e.g. a central-lab file) become
Collected/Vendor flagged to confirm, other unannotated tests stay blank + orange; all
other parents are inherited). The value-level-only rule then blanks the Variables row.

It never modifies `--skeleton` (that is the backup) and rebuilds `--out` each run.
Read its printed counts and `REVIEW` lines, then run `self_qc.py`. Keep the script
**general** — a study quirk goes in as an input/argument, never as a hard-coded
study ID, path, domain list or value.

## Working conventions (apply to every edit)

- **Back up before editing.** `shutil.copy(F, F.replace('.xlsx','_pre_<change>_backup.xlsx'))`; one backup per pass.
- **Highlight only what needs review — do not highlight every change.** Use a
  single **orange** fill (`PatternFill('FFC000')`) and reserve it for cells a human
  must look at: a value you couldn't source, a spec/aCRF conflict, a missing
  codelist, an unresolved item. A routine filled-from-spec cell gets **no fill** —
  blanketing the whole workbook in "I changed this" highlighting buries the few
  cells that actually need attention and makes the deliverable unusable. (Track what
  changed via the `_pre_*_backup.xlsx` diff, not fill color.) Leave the template's
  own required-cell shading (e.g. `FDE9D9`) untouched.
- **`Programmer Review` column.** Add this non-standard column (P21 ignores it). For any value that is **overridden** (aCRF/data over spec) or **uncertain/conflicting**, keep the accepted value and record the **original value + reason** here — never silently change. See the guardrail below.
- **PermissionError = file open in Excel.** On `wb.save(F)` PermissionError, save to `F.replace('.xlsx','_updated.xlsx')` and tell the user. (Files under OneDrive-synced folders have also *vanished* mid-task — if the target is missing, rebuild from the latest `_pre_*_backup.xlsx`.)
- **Preserve referential integrity.** Every Method/Comment/Codelist ID referenced must resolve; the workbook must re-open cleanly (`openpyxl.load_workbook`) after each pass.
- **Fill-empty-only.** Never overwrite values already present; report what couldn't be sourced. When a P21-skeleton value (typically its guessed Origin) disagrees with the spec, keep it, highlight it orange and record `skeleton=… spec=…` in Programmer Review — the programmer decides. Summarise these conflicts for the user by pattern (e.g. `--TESTCD`/`--CAT` Assigned vs CRF, `VISIT` Assigned vs Derived) rather than one by one.
- Environment: Python 3.12 + openpyxl; PyMuPDF/`fitz` for the aCRF; pyreadstat for `.xpt`; python-docx for cSDRG/ADRG; reportlab for supporting PDFs. `PYTHONUTF8=1`. See [references/environment.md](environment.md).

## Prepare

1. Back up.
2. **Verify the define-level metadata P21 pre-filled** (study ID, SDTMIG /
   Define-XML / CT versions) against the TD spec / data standards catalog;
   complete any P21 left blank.
3. **Identify the study column** in the TD spec — locate the column whose **header
   matches the study ID** (StudyName). Confirm by header, not a fixed index
   (positions differ per workbook).
4. **Confirm domain inclusion** — a domain is in scope only if marked `x` in the
   study column of the **Content tab**.

## Reading the TD (compound) SDTM spec

Per-domain tabs plus `Study` and `Content` tabs; each study is a column.
Domain-tab columns (verify per workbook): `N`=Conversion Definition,
`O`=Programming Notes; the study column carries inline markers; Variable-Category
`M`=main, `S`=supplemental qualifier (→ SUPP--). Markers: `x`=in scope,
`[r_page] N`/`[r_pages]`=CRF page override, `[r_orig] CRF`=origin CRF,
`[r_prog] …`=derivation note, `[r_sort]`=key sequence. Column layout differs per
workbook — confirm indices from the header row, not a fixed number (study columns
and Origin/Pages/Conversion/Notes often sit at different positions than the default
`N`/`O`, and the notes column may be titled `SAS Codes`). Study-column headers can
be formulas (`=Study!B1`) — read with `data_only=True` and match the header to the
study ID ignoring case and punctuation. When a domain tab repeats a variable row,
use the row marked for this study.

**A single study-column cell can CONCATENATE several markers** — e.g.
`[r_orig] CRF [r_pages] 98` reclassifies origin **and** overrides pages at once.
Parse **each** `[r_*]` tag on its own, never `split(']')` (which captures the tail
of the next tag as your value and silently drops both). Use one regex per tag:
`\[r_orig\]\s*([A-Za-z]+)`, `\[r_page[s]?\]\s*([0-9][0-9 ,]*)`,
`\[r_prog\]\s*(.*?)(?=\[r_|$)`. A study `[r_orig]` **overrides** the base Origin
column for that study (the base may say Assigned while the study cell says CRF).

**Method/Comment text source priority (copy verbatim):**
`[r_prog]` › **Conversion Definition (col N)** › **Programming Notes (col O)**.
*(N before O — the primary derivation first.)* If N is too general, or N ≠ O
substantially, still fill from the priority pick but flag both in Programmer
Review. All empty → leave blank and report.

**Expand METHODS-tab pointers — the fill must DO this, not just copy the pointer.**
The Conversion Definition is often a **pointer** to a standard method on the
compound spec's `METHODS` tab (`--SEQ`, `--STDY`, `--ENDY`, `--DY`, `--LOBXFL`,
`--BLFL`, `--SPID`, `--STRESN`, `--ENRF*`, `--STRF*`, `EPOCH`, `USUBJID`, `VISIT`,
`VISITNUM`, `VISITDY`, `TAETORD`, `RDOMAIN`). When the method text matches a
METHODS-tab name, write the **full algorithm from that tab with `--` replaced by
the domain code** — e.g. `MT.AE.AESTDY` = "AESTDY = (date portion of AESTDTC) −
(date portion of RFSTDTC) +1…", **not** the literal `--STDY`. `scripts/self_qc.py`
flags any method Description left as a bare pointer.

- **Rejoin `--` split by a line wrap before substituting** — METHODS text often
  breaks `--` across lines (`-
-DTC`, `--
STDY`); substitute after rejoining or the
  output keeps a literal `-
-DTC` / `AE
STDY`.
- **Expand pointers in Assigned Comments too**, not only Methods (e.g. an Assigned
  `--ENRFTPT` or `VISIT` must not ship as the bare pointer).
- **Pointer ≠ variable stem → flag, don't trust.** If the spec's pointer does not
  match the variable's own stem (`MHSTDY` whose Conversion Definition says `--DY`
  instead of `--STDY`), the expansion describes the wrong variable. Still fill from
  the priority pick, but highlight the Method orange and record the Programming
  Notes text in Programmer Review for the programmer to choose.

**Also match by variable name/stem when Conversion Definition is empty.** A Derived
variable often has *no* conv/notes text because its algorithm is the standard one
on the METHODS tab — look it up by the **variable name** (`VISITNUM`, `EPOCH`,
`USUBJID`, `VISIT`, `VISITDY`, `TAETORD`) or by its **domain-stripped stem**
(`ECSEQ`→`--SEQ`, `AUDY`→`--DY`, `AESTDY`→`--STDY`) and expand that, rather than
leaving the Method blank (DD0042). Do this in the main fill, not only as a QC
afterthought — Derived vars such as `VISITNUM`, `EPOCH`, `RELREC.USUBJID` commonly
have empty conv text and would otherwise ship with no Method.

## Origin & Source — version-aware

The valid Origin set depends on the **Define-XML version declared in the define
spec**. 2.0 uses `CRF`/`eDT`; 2.1 uses `Collected` + a `Source`
(`Investigator`/`Subject`/`Vendor`/`Sponsor`). Convention: **Derived → Method,
Assigned → Comment**.

**Only Derived variables get a Method.** A **CRF / Collected** variable is captured
on the CRF, not computed — it carries a page, **not a Method**. Never attach a
Method (or a method pointer) to a Collected/CRF/eDT/Vendor origin; the value comes
from data collection, and a spurious Method both misdescribes the variable and
trips P21. Same at value level. (Assigned → a Comment, not a Method.)

**Use the official Origin Type definitions (CDISC Define-XML CT, codelist C170449)
— quote them, don't paraphrase from memory.** In particular Predecessor is "a value
that is copied from another variable" (not limited to another dataset), and Derived
is "calculated by an algorithm or reproducible rule". When asked which origin fits,
cite the CT definition (and the SDTMIG variable description, e.g. `--STRESC` "copied
or derived from `--ORRES`"); when the spec is silent and two origins fit, ask the
user for the team convention.

Full version-aware mapping, the official definitions, the complete origin/source
sets, Predecessor-vs-Derived guidance and the annotation-vs-spec conflict rule:
[references/origin-source-mapping.md](origin-source-mapping.md).

## CRF pages

Priority: study `[r_page]` override → domain-tab **base Pages** column → derive
from the **aCRF**. Required for Collected/Investigator & Subject (2.1) / CRF (2.0);
Vendor data needs no page. The aCRF is authoritative for page **values**; on
disagreement the aCRF wins **but** the original spec page + reason goes into
`Programmer Review`. The extraction (four filters + box-fill-color→domain) and the
conflict rules are in [references/acrf-page-derivation.md](acrf-page-derivation.md);
use [scripts/acrf_annotations.py](../../scripts/acrf_annotations.py) rather than
rewriting it. **Fallback:** when the color-filtered extractor finds no page for a
Collected/Investigator variable, do a looser name-match scan of the aCRF before
flagging — the domain-color filter can exclude a genuine annotation
(`acrf_annotations.name_scan()`). Only after that scan also fails do you flag it
(truly-absent Collected vars are usually vendor-assay → Source Vendor).

**Pages = the actual PDF page number** (team rule) — the page a define.xml link
opens (`PhysicalRef`), **not** the number printed in the CRF footer. An aCRF with
front matter (a generated-on cover, a TOC) has PDF page = printed page + cover
count, e.g. the AE form printed "100 of 107" is PDF page 101. `fill_define.py`
defaults to `--page-ref physical`. The TD spec's own Pages column is often numbered
by the printed footer: the script **detects the spec's basis** (votes over variables
with both a spec and an aCRF page) and shifts spec pages to PDF numbering before
comparing or falling back, so a correct spec page does not raise a false
spec≠aCRF note. A spec page beyond the aCRF's page count is stale — never use it;
flag it. Never mix numbering bases in one define. If the spec's own pages are
**mixed** (e.g. some `[r_page]` overrides already PDF-numbered, others printed — no
basis wins ≥80% of votes), do not shift at all; flag every spec-only fallback page
as basis-uncertain and tell the user so the spec owner can fix it.

## SUPP-- standard variables — fixed comment template

Every `SUPP<domain>` dataset shares the same structural variables with the **same
Origin and the same standard Comment**. **Fill only the six rows marked "fill"
below** (reuse one shared Comment ID per text — these describe the variable, so they
take precedence over a generic `COM.NODATA` even on a no-data SUPP dataset). Leave
the other rows alone: `QEVAL` is populated from the source spec (do **not**
overwrite it), `QVAL` origin is value-level, and `STUDYID`/`USUBJID` are standard.

| Variable | Origin (Source) | Comment | Fill? |
|---|---|---|---|
| `STUDYID` | Protocol (Sponsor) | — | no |
| `RDOMAIN` | Assigned (Sponsor) | Domain abbreviation from where data originated. | **fill** |
| `USUBJID` | Derived (Sponsor) | *(its `MT.<DS>.USUBJID` method)* | no |
| `IDVAR` | Assigned (Sponsor) | Name of the variables for the related records. | **fill** |
| `IDVARVAL` | Assigned (Sponsor) | Value of identifying variable described in IDVAR. | **fill** |
| `QNAM` | Assigned (Sponsor) | Assigned based on origin described in QVAL VLM section | **fill** |
| `QLABEL` | Assigned (Sponsor) | Assigned based on origin described in QVAL VLM section | **fill** |
| `QVAL` | *(value level — blank at variable level)* | *(per-`QNAM` in ValueLevel)* | no |
| `QORIG` | Assigned (Sponsor) | Assigned based on origin described in QVAL VLM section | **fill** |
| `QEVAL` | Assigned (Sponsor) | *(from source spec — leave as-is)* | no |

(`RELREC` shares `RDOMAIN`/`IDVAR`/`IDVARVAL` and takes the same three comments.)

## ValueLevel

SUPP `QVAL` rows: source each `QNAM` from its qualifier's parent-domain row, then
apply the same Origin/Pages/Method/Comment rules. **Everything the Variables tab
gets, ValueLevel gets too** — the same eDT→Collected/Vendor mapping, and Derived
value-level rows need a **Method** (not a Comment).

VLM (optional) adds domain value-level. **First confirm the VLM file actually
covers this study** — a compound VLM may carry columns for only some studies. If
the target study's column is absent, do **not**
reuse another study's VLM rows — flag that the VLM lacks a column for this study and
leave that domain's value-level for the programmer (no-fabrication). **Build the
Where Clause by splitting
`WhereVarList` / `Comparator` / `WhereValue` each on `;`, zipping into
`VAR CMP VALUE` conditions, joined by `AND`** — `IN` keeps the comma-separated
value list, `EQ` quotes values containing spaces or commas (use double quotes
when the value itself contains `'`). Example:
`QSORRES; QSTESTCD` / `EQ; IN` / `NOT AT ALL; ITEM01, ITEM02` →
`QSORRES EQ 'NOT AT ALL' AND QSTESTCD IN ITEM01, ITEM02`. Only rows marked for this
study are added; a VLM Length above the variable's data Length is capped to it
(DD0123) and noted; when a VLM row has both Conversion Definition and Programming
Notes that differ, use N and record O in Programmer Review.

Consistency: **DD0074** — a variable's Origin must match *every* value-level
Origin; when a result variable has per-value origins that differ (e.g. `AU.AUORRES`,
`QS.QSSTRESC` where some values are Assigned and some Derived), **clear the
variable-level Origin** so origin is defined at the value level only.

**Reviewer convention (applies to SDTM and ADaM): once a variable has value-level
metadata, its Origin, Source, Pages, Method, Predecessor and Comment live only on
the ValueLevel rows — leave all of them blank on the Variables row**, even when every
value shares one origin (model: ADaM ADEG AVAL/AVALC; SDTM --ORRES/--STRESC per
--TESTCD, SUPP QVAL, TS.TSVAL). Clear the Variables row only after confirming every
ValueLevel row of that variable carries its own Origin (+Pages/Predecessor/Method/
Comment as applicable); record the cleared values in Programmer Review. Timing vars
consistent across datasets (DD0110); value-level Length ≤ variable Length (DD0123).

## Self-QC pre-check (before generating define.xml)

Run [scripts/self_qc.py](../../scripts/self_qc.py) against the workbook to catch the
spec-checkable rules and cut P21 round-trips. **It is a pre-filter, not
authoritative** — ~220 of the ~279 catalog rules need the *generated* define.xml,
the CT database, MedDRA, the standard-label DB, or the data, so always still
generate define.xml and run the P21 Define validation.
[references/rule-catalog.md](rule-catalog.md) is the coverage map — the
full 279-rule catalog as ID + short title, marking which `self_qc.py` implements
(38), which are candidate spec-checkable gaps to add (27), and which are P21-only.
The checker covers the
**ValueLevel tab as well as Variables**, flags **non-integer Length** (page
numbers leaked into Length → OD0013) not just empty, treats **MedDRA/WHODD/LOINC
as dictionaries**, and does not false-flag valid SDTM roles.

```
python scripts/self_qc.py <define_spec.xlsx> [--acrf <acrf.pdf>] [--package <submission folder>]
```

`--acrf` checks every Pages cell (Variables and ValueLevel, QNAM for SUPP rows)
against the annotations on that physical PDF page. `--package` checks that every
document on the Documents tab is in the folder and that no reviewer's guide
(.docx) still has unaccepted tracked changes. The checker also flags Origin/Source
disagreement, Assigned-style comments on Collected variables, "Set to --ORRES"
copies that are not Predecessor, unreadable method/comment wording, and TS
TSVAL/SDTIGVER problems (see the review checks below).

## Review & recheck checks (from define-package reviews)

Apply these when reviewing a define package or rechecking it after updates.
Record each finding in the review workbook with its current value and cause,
not only in chat.

1. **Recheck every page link after any aCRF update.** An update can *replace*
   an annotation instead of adding one. For example, a collection-date annotation
   can be swapped for an EDC date stored in SUPP--, which leaves the original
   `--DTC` pointing at a page where it is no longer annotated. Rerun
   `self_qc.py --acrf` on the new aCRF, and when a pending item says "aCRF
   updated", confirm it against the actual file, not the note. Check the
   file date first: a resolution can be logged before the updated aCRF is put
   in the folder.
2. **Origin and Source must agree.** Assigned / Derived / Protocol / Predecessor
   take Source = Sponsor. Collected takes Investigator, Subject or Vendor (Vendor
   has no pages). When a reviewer changes an Origin, also change the Source and
   add or remove the Comment, Method and Pages to match. A Collected variable
   must not keep an Assigned-style comment ("One on one mapping based on
   codelist"). When the aCRF only shows a conditional record (e.g. `--STAT = NOT
   DONE when --TESTCD = --ALL`), the test code is not collected for the other
   records: keep it Assigned, or set origins per value at value level. A comment
   that only says "Set to --ORRES" describes a copy: use Predecessor.
3. **Annotated on the aCRF but not in the data.** If a QNAM or variable is
   annotated but absent from the SDTM data (and from the TD spec for this study),
   do not add it to the define and never invent its label, length or origin. Mark
   it `[NOT SUBMITTED]` on the aCRF (or remove the annotation). Add it to the
   define only after it is in the TD spec and the data. This often happens when a
   study's aCRF is annotated from a sibling study's template.
4. **Method / Comment wording must read as plain English.** No librefs
   (`sdtm.EX`), SAS functions or formats (`catx(`, `put(`, `best.`), raw dataset
   or variable names, references to the spec layout ("tab Content", "key
   variables column", "sheet X"), template placeholders (`"XX"`, `[if ...]`), or
   unbalanced quotes. State sort keys and concatenation parts by name.
5. **TS consistency.** TSVAL over 200 characters continues in TSVAL1..n, in the
   data *and* the define. TS SDTIGVER/SDTMVER must match the IG version the
   define declares and the reviewer's guide states. Before changing either side,
   confirm which version the data were actually built to (e.g. the study
   metadata or the data standards catalog). A planned maximum age with no upper
   limit uses TSVALNF = PINF, not NA. TS text values (OBJPRIM, TITLE) should
   match the protocol wording. Changing the spec comment alone is not a fix:
   regenerate TS from the corrected source.
6. **Package consistency.** Every document the define links to (e.g. the
   reviewer's guide PDF) is in the package folder. The reviewer's guide has no
   unaccepted tracked changes and its document properties show current versions.
   Dictionary versions (MedDRA, WHODD, LOINC, UNII, MED-RT) agree across TS, the
   define and the reviewer's guide.

## Codelists, Standards & Documents

Standard codelists carry an NCI Codelist Code + a Terminology version that must
reconcile with the declared CT **Standards** row (else DD0021/DD0127/DD0138/DD0150).
Codelist Names must be unique (DD0131) — when two per-domain codelists share a
display name (`LBTEST`/`LCTEST` both "Laboratory Test Name", `IETEST`/`TITEST`,
`LBCAT`/`LCCAT`, and auto-named `QVAL.SUPPxx.*` value-level codelists),
**disambiguate by appending the domain in parentheses** (`Laboratory Test Name
(LB)` vs `(LC)`); borrow a clean sibling study's names for parity. A **missing CT
codelist you can't source**
→ give the reference the `DATASET.VARIABLE` name, **highlight the Codelist cell
orange**, and flag in Programmer Review — never invent terms. Register supporting
PDFs on the Documents tab and link the Methods/Comments that reference them.

Also set the **Datasets tab `Standard` column** per-dataset (`SDTMIG <version>`) — not
just the Standards tab; both are needed and the per-dataset column is easy to miss.

**Verify dataset-level metadata against the Content tab — don't trust a malformed
P21 skeleton.** The P21-generated define can carry a wrong `Class`, blank
`Structure`, or blank `Key Variables` for a dataset (a sponsor-defined domain
such as a "demographics as-collected" `DC` can come through as `Class=SYSTEM` with
no Structure/Key). Replace an invalid Class only when the Content tab's class is a
valid Define-XML class; if the Content tab is also invalid (e.g. `CUSTOM DOMAIN`),
leave it, highlight orange and ask the user (DD0055).
Source `Class` / `Structure` / `Key Variables` (and Purpose/Repeating) from the TD
spec's **Content tab** row for that dataset — a domain that parallels a standard one
(as-collected `DC` ↔ `DM`) takes the same class and structure. Fill DataType/Length
from the spec (order used by `fill_define.py`: same SUPP/RELREC structural variable
populated elsewhere in this define → TD spec Type/Length → sibling define), noted in
Programmer Review — for any variable the skeleton left blank (MD0034/OD0070),
including SUPP-standard and RELREC vars (`text`, lengths from a populated sibling SUPP);
date-type variables must carry a date type (`--DTC`/BRTHDTC/DTHDTC, DD0149) and an
**empty** Length (DD0068).
Coded variables reference their **dictionary** (`--DECOD` → `MedDRA`, `CMDECOD` →
`WHODD`) on the Dictionaries tab, not a codelist.

## Generate & validate

Generate define.xml → **download the P21 Define issue report** → triage each
finding: **define-metadata** (fix in workbook) vs **data/programming** (a
punch-list deliverable for the SDTM programmer — do not touch the define).
Iterate. Rule-by-rule recipes and the punch-list format:
[references/p21-remediation.md](p21-remediation.md).

## cSDRG / ADRG

Keep domain labels consistent with the define, fill conformance explanations from
the actual issues, fill narrative sections from a completed sibling-study RG, and
render tracked-changes when asked: [references/csdrg.md](csdrg.md).

## Two authority modes when syncing to updated sources

- **Data-authoritative** — only add/keep what exists in the actual data.
- **Spec-authoritative** — add the spec's domains/vars/qualifiers (gated by the
  Content-tab checkbox) even if not yet in data. Confirm which before a big sync.
